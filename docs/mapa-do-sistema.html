1. Arquitetura

Três camadas desacopladas

O frontend é um conjunto de páginas HTML servidas de forma estática. Ele fala com a API REST por JSON e Bearer token. A API fala com o Postgres por SQLAlchemy via pooler do Supabase. Não há servidor de templates: toda renderização acontece no navegador.

Apresentação

frontend/

  • 12 páginas HTML, Tailwind via CDN, Material Symbols
  • js/app.js (1.728 linhas) concentra carrinho, catálogo, checkout e conta
  • admin.html (2.918 linhas) carrega seu próprio script de painel
  • Fallback offline: catálogo e pedidos ficam em localStorage quando a API está fora
  • Deploy alvo: Vercel (vevey.vercel.app)
Negócio

backend/app/

  • FastAPI com prefixo /api/v1, Swagger desligado em produção
  • 5 routers: auth, produtos, pedidos, frete, funcionarios
  • JWT HS256 (PyJWT) com claim role, senha em bcrypt
  • Rate limit global 120/min (slowapi) e limites por rota no login e checkout
  • Headers de segurança OWASP e handler 403 customizado
  • Serve /assets do frontend para imagens WebP
  • Deploy alvo: Render (vevey-api.onrender.com)
Persistência

database/

  • PostgreSQL gerenciado no Supabase, região sa-east-1, pooler na porta 6543
  • schema.sql: DDL inicial com 9 tabelas, índices e 3 triggers
  • alteracoes_schema.sql: migra CHECKs para enums nativos, cria usuarios_admin e tipo_entrega
  • Sem Alembic: migrações são SQL manual no editor do Supabase
  • Seed por backend/seed.py ou seed.sql

3. Ciclo de vida

Estados do pedido e do pagamento

Todo pedido nasce em Aguardando Pagamento, seja pelo checkout web, pelo checkout autenticado ou pelo pedido manual do WhatsApp. A transição seguinte é feita pelo painel administrativo, que grava uma linha de histórico a cada mudança. O cancelamento devolve estoque por trigger.

Pedido (status_pedido)

Pendente→ Aguardando Pagamento→ Pago→ Pronto para Retiradaou Enviado para a Transportadora→ Enviado→ Entregue · a qualquer momento → Cancelado

"Pendente" é o default da coluna, mas nenhuma rota cria pedido nesse estado. O painel exibe ainda "Em Separação", que não existe no enum do banco.

Pagamento (status_pagamento)

Pendente→ Aprovado| Recusado| Em Análise| Estornado

Nenhum webhook real existe. O único caminho para "Aprovado" é a rota de simulação aprovar-teste, que hoje falha (ver achados).

Tipo de entrega

RETIRADA_LOJA ENVIO_TRANSPORTADORA

Na retirada, a API grava o endereço fixo da loja (R. Sen. Flaquer, 691, Centro, Santo André). O pedido manual sempre usa envio por transportadora.

9. Discussões

Modelagem para a migração Laravel + Filament

Registro das discussões de 2, 3, 4 e 8 de novembro de 2026 sobre o que mudar no modelo de dados antes de reescrever o sistema em Laravel com Filament. Os dois temas abertos por Richard foram armazenamento de dinheiro e um ledger de estoque. O restante são pontos levantados na leitura do código. Estas discussões servem de base para os ADRs do projeto novo: cada bloco “decidido” deve virar um ADR com contexto, opções, decisão e consequências.

9.1 Dinheiro

O problema atual não é o tipo da coluna. NUMERIC(10,2) é correto. O valor vira float na borda: a API serializa com float() e o JavaScript multiplica preço por quantidade em ponto flutuante. Cupom e desconto Pix são calculados só no navegador e nunca chegam ao banco. A tabela de pagamentos não tem valor próprio.

Armazenamento

  • Inteiro em centavos, coluna bigint, com value object Money no Laravel via brick/money atrás de um cast Eloquent.
  • NUMERIC também funciona, mas o cast decimal do Laravel devolve string e um cast acidental para float traz o problema de volta. Inteiro elimina a classe de erro.
  • Filament formata direto com money('BRL', divideBy: 100).
  • A loja só opera em real: sem coluna de moeda.

O que guardar, mais importante que o tipo

  • Totais são fatos históricos, não derivações do preço atual do produto.
  • No item, que é a linha do pedido (hoje itens_pedido): snapshot de nome e SKU, preço unitário praticado, desconto alocado na linha, total da linha. Snapshot significa copiar para a linha, no momento da venda, os dados que descrevem o que foi vendido. Se o produto for renomeado ou tiver o preço alterado em junho, o pedido de março continua contando a história de março. O produto_id fica como referência para navegar ao cadastro atual, nunca para reconstruir a venda. Soft delete garante que a referência não quebra; snapshot garante que o histórico não muda. Precisa dos dois.
  • No pedido: subtotal, desconto, frete, total, com CHECK no banco garantindo total = subtotal - desconto + frete.
  • Tabela de ajustes do pedido: tipo (cupom, desconto Pix, frete grátis, ajuste manual), valor, base de cálculo e quem aplicou. Hoje existem três descontos e nenhum é persistido.
  • Desconto de pedido rateado por linha. Necessário para devolução parcial de pedido com cupom e para NF-e, que exige valor por item. Money::allocate() faz o rateio sem sobra de centavo.
  • Arredondamento decidido uma vez, no nível do pedido, e o resultado gravado. Nunca recalcular.

Pagamentos

  • Hoje 1:1 com o pedido e sem valor. Deve ser 1:N: Pix expira e outro é gerado, cartão recusado é tentado de novo, estorno pode ser parcial.
  • Cada pagamento: valor, provedor, id no provedor (único por provedor, não global), status, expiração.
  • Tabela de eventos de pagamento com payload bruto do webhook e chave de idempotência por evento.
  • Regra de ouro: webhook dispara, GET no provedor é a verdade. O webhook só avisa que algo mudou; o status gravado vem de uma consulta ao provedor.

9.2 Estoque: ledger simples ou double-entry

Veredito: ledger de lançamento simples agora, double-entry só quando houver mais de um local físico.O que se quer de um ledger é imutabilidade, auditoria e saldo derivável. Isso vem com uma linha por movimento, quantidade com sinal, motivo, referência e ator. Double-entry adiciona uma invariante a mais: todo movimento soma zero entre contas. Ela só paga quando existem várias contas reais entre as quais o estoque se move. Com uma loja só, a segunda perna é sempre uma conta virtual (fornecedor, cliente, perda), ou seja, o enum de motivo com outro nome.
Por que um ledger e não só um UPDATE atômico (pergunta de 03/11).Um UPDATE stock_levels SET on_hand = on_hand - 3 WHERE product_id = ? AND on_hand >= 3 resolve concorrência, e continua existindo: é o que stock_levels faz dentro da transação com lock. O que ele não dá é explicabilidade. Sobra só o número atual, e quando alguém perguntar "por que tem 7 se comprei 20 e vendi 10?" não existe resposta. Estoque físico diverge sempre: quebra, erro de contagem, brinde, devolução não lançada. Sem histórico só dá para corrigir o número, nunca achar onde divergiu. O ledger é um insert a mais na mesma transação e compra auditoria (quem, quando, por quê, referência), reconciliação na contagem física (contado versus soma dos movimentos, com a linha exata da divergência), reversão limpa (cancelamento vira movimento compensatório), idempotência (o unique na referência impede que um webhook repetido baixe duas vezes) e relatórios por GROUP BY. Custo real: uma linha por movimento e a disciplina de que todo ajuste passa por um único serviço. on_hand nunca é campo editável no Filament; só existem as ações "registrar venda" e "contagem / ajuste".

Quando migrar para double-entry

  • Segundo local físico (depósito, evento, consignação).
  • Transferência entre locais como operação diária.
  • Valoração de estoque com custo por movimento (CMV).
  • Nesses casos o movimento ganha from_location e to_location; o resto da estrutura continua igual.

O que double-entry não resolve: reserva

Hoje o estoque é debitado na criação do pedido e um Pix nunca pago segura estoque para sempre. Reserva é uma pretensão sobre o estoque, não estoque em algum lugar. Até o Odoo, referência em estoque double-entry, mantém o reservado como contador à parte e só afeta o saldo quando o movimento é concluído.

As três tabelas

Por que qty com sinal e direction gerada, e não direction gravada pela aplicação.Direction é cem por cento derivável do sinal. Dois campos escritos pela aplicação para um fato só podem discordar, e o banco aceitaria a linha. Como coluna gerada stored, o banco calcula na inserção, a aplicação não consegue escrever nela, e ela ainda pode ser indexada e filtrada. Limitações conhecidas e aceitas: a expressão não se altera com ALTER (derruba e recria), mudar o tipo de qty exige derrubar direction antes, e colunas geradas stored não entram em replicação lógica antes do Postgres 18. Nenhuma dessas afeta as mudanças realistas nesta tabela. A validação de reason contra sinal (sale sempre negativo, purchase sempre positivo) fica no enum PHP. Duas colunas qty_in e qty_out, no estilo kardex, foram descartadas: metade das células vazias, CHECK de exatamente uma preenchida e toda soma vira duas. O kardex é exibido no Filament a partir de qty.

Ciclo de vida

  • Checkout: numa transação, lockForUpdate na linha de stock_levels, confere o disponível, cria a reserva com expiração igual à do Pix.
  • Pagamento confirmado: reserva vira fulfilled e nasce um movimento negativo com motivo venda. É aqui que o físico sai.
  • Cancelado ou expirado: reserva vira released. Nenhum movimento, porque nada saiu.
  • Venda de balcão: é um pedido com channel pos, pago na hora. Movimento direto, sem reserva.
  • Devolução: movimento positivo criado explicitamente pelo operador. Produto que volta estragado não volta ao estoque.
  • Recontagem: movimento de ajuste com ator e observação. Hoje o ajuste é um PATCH que sobrescreve o número e apaga a história.

Guardas

  • Job diário recalcula on_hand a partir do ledger e compara com o cache. Drift vira alerta, não correção silenciosa.
  • O unique na referência mata a classe de bug atual, em que API e trigger debitam o mesmo item duas vezes.
  • Quantidade é inteiro. Item vendido por peso vai em gramas, pelo mesmo motivo dos centavos.
  • Estoque negativo é política. decidido em 03/11/2026 Online e WhatsApp nunca passam do disponível, regra no serviço de reserva. Balcão com o produto na mão pode passar: sem CHECK on_hand >= 0 no banco, e on_hand < 0 vira alerta no painel ("lance a entrada ou faça contagem"), não erro. Detalhe em 9.6.

9.3 Outros pontos do modelo

  • Status do pedido mistura três coisas: pagamento, expedição e tipo de entrega. Separar em payment_status, fulfillment_status e delivery_method. "Em Separação", que o painel exibe e o banco não conhece, vira um fulfillment_status.
  • Carimbos de transição no pedido: paid_at, cancelled_at, shipped_at, delivered_at. Relatório por período sem varrer histórico.
  • Canal no pedido. decidido em 03/11/2026 orders.channel, string com cast para enum PHP (web, pos, whatsapp), definido na criação e imutável. Decorre da decisão de que venda de balcão é um pedido (9.6). Hoje o canal só é inferível pelo prefixo do número. Relatórios por canal e mês saem de orders agrupado com paid_at.
  • Vendedor no pedido. decidido em 04/11/2026: coluna nullable desde já orders.seller_id, FK users, nulo na venda web e preenchido no balcão quando houver quem informe. Ranking por vendedor e comissão ficam para quando o stakeholder pedir; a coluna já existe para não exigir migration depois. Hoje o vendedor aparece como nome em texto livre no histórico.
  • Número do pedido como coluna gerada uma vez, não derivada do id. Hoje o fluxo manual gera prefixo diferente do checkout para o mesmo id. Não expor id sequencial em URL pública.
  • Checkout sem login não cria conta com senha. Pedido recebe snapshot do comprador (nome, email, telefone, CPF) e customer_id preenchido sempre que o cliente for identificado por uma identidade (9.9); senha fica nula até o cliente ativar a conta. Hoje são criados clientes com senha placeholder que ocupam email e CPF e nunca logam.
  • Endereço de entrega é snapshot no pedido, não FK para endereço do cliente. Retirada não tem endereço. Hoje o backend grava o endereço da loja como endereço do cliente e o pedido manual inventa um CEP de São Paulo.
  • Staff e clientes em tabelas e guards separados. Filament autentica em users com canAccessPanel; a loja autentica em customers.
  • Monólito modular e RBAC. decidido em 04/11/2026 A arquitetura do projeto novo é um monólito modular; Richard vai detalhar. Autorização por RBAC em módulo próprio (permissions, ver ADR 8): os papéis da equipe (três no repo, dois no documento do TCC) viram dados desse módulo, não enum.
  • Soft delete em produtos, clientes e funcionários, no lugar da lógica "inativa se tiver venda".
  • Cupons viram tabela: código, tipo, valor, mínimo, vigência, limite de uso. Hoje VEVEY10 é literal no JavaScript.
  • Produto precisa de SKU e código de barras para o balcão. decidido em 03/11/2026: catálogo plano, sem product_variants Cada cor é um produto com SKU e saldo próprios ("por mais que seja um balão, não deixa de ser outro produto"). Ledger, reservas e linhas de pedido apontam sempre para products. Filtro por cor e tipo vem de atributos genéricos (9.7), nunca de coluna color solta. No Filament, ação "duplicar produto" para cadastrar cores em série.
    O que é SKU. Sigla de Stock Keeping Unit, unidade de manutenção de estoque. É o código interno, definido pela loja e legível por humanos, de cada item contado separadamente no estoque. Exemplo: BAL-MET-18-ROSE para o balão metalizado de 18 polegadas rose gold; a versão prata é outro SKU, porque o estoque de um não serve para o outro. O SKU identifica o produto, não o lugar onde ele está: o mesmo balão tem o mesmo SKU na loja, no depósito e numa feira. Com mais de um local, o que se multiplica é o saldo (uma linha em stock_levels por par produto e local), nunca o código. Difere do código de barras (EAN/GTIN), que é impresso pelo fabricante e igual em qualquer loja; um kit montado pela Vevey tem SKU mas não tem EAN. Serve para a operadora bipar ou digitar no balcão, para o ledger de estoque identificar o que saiu, e para o snapshot do item do pedido continuar identificável mesmo que o produto seja renomeado. Hoje o repositório só tem id e slug, e slug é feito para URL, não para operação.
  • Enums como string no banco com enum PHP no modelo, não enum nativo do Postgres. O arquivo de alterações mostra o custo: para adicionar um valor foi preciso derrubar trigger e alterar tipo. Filament usa HasLabel e HasColor para badges.
  • Nenhum trigger no banco. decidido em 02/11/2026 Débito de estoque, histórico e totais em código, dentro de transação com lockForUpdate. Constraints declarativas (CHECK, UNIQUE, FK) continuam; só a lógica procedural sai do banco. O Eloquent não sabe que o trigger existe; foi isso que causou o débito duplo.
  • Ator em tudo que o funcionário faz: created_by em movimentos, ajustes, pedidos manuais e mudanças de status. Hoje o histórico guarda o nome em texto livre.
  • timestampTz nas migrations. O default do Laravel em Postgres é timestamp sem fuso.
  • Nomenclatura padrão Laravel, em inglês. decidido em 02/11/2026 Tabelas no plural em snake_case (products, order_items, stock_movements), modelos no singular em PascalCase (Product, OrderItem), chaves estrangeiras como product_id, pivots em ordem alfabética no singular (category_product), colunas created_at, updated_at, deleted_at. Seguir a convenção evita configurar $table, $foreignKey e nomes de pivot em cada modelo, e deixa o Filament gerar resources e relation managers sem ajuste. O português fica na interface, via labels e traduções, nunca no schema. O schema atual (produtos, itens_pedido, usuarios_admin) não é migrado com os nomes; é recriado.
  • Imagens via spatie/laravel-medialibrary. decidido em 02/11/2026 Sai a coluna imagem_url e o upload em disco do servidor da API. O pacote cria a tabela media polimórfica, guarda os arquivos num disk configurável (S3 ou Supabase Storage em produção) e gera conversões WebP em tamanhos fixos por fila. O Filament tem o campo SpatieMediaLibraryFileUpload pronto para o formulário de produto.

O que preservar do modelo atual: snapshot de preço no item, tabela de funcionários separada, RESTRICT nas FKs de venda e histórico de status como tabela própria.

9.4 Snapshot na linha do pedido ou versão de produto

decidido em 02/11/2026: snapshot na linha, sem histórico de versões de produto

Contexto

O pedido precisa continuar contando a história da venda mesmo que o produto seja renomeado, reprecificado ou excluído depois. Richard perguntou se gravar o histórico do produto e apontar a linha do pedido para uma versão resolveria, com a ressalva de que aumentaria o número de joins.

Opções consideradas

  • A. Versão de produto. Tabela product_versions imutável; cada edição cria uma versão nova; order_items.product_version_id aponta para ela. Congela nome, SKU, descrição e imagem.
  • B. Snapshot na linha. order_items copia, no momento da venda, os dados que descrevem o que foi vendido: SKU, nome, preço unitário, desconto da linha, total da linha. Opcionalmente product_snapshot jsonb com descrição e imagem como o cliente viu.
  • C. Ambos. Descartado por redundância.

Análise

  • A versão cobre atributos do produto, mas não cobre fatos da venda. O mesmo produto, na mesma versão, sai a preços diferentes: site, cupom, desconto dado no balcão, promoção. Preço praticado, desconto e total têm que estar na linha de qualquer forma. A versão substituiria só nome e SKU, ao custo de um subsistema inteiro.
  • O join não é o custo real. Um join por chave primária é barato. O custo está em toda edição virar versão (ou numa regra de quais campos versionam, que ninguém lembra seis meses depois), no Filament trabalhar contra o fluxo (o save natural é UPDATE; versionar exige interceptar e mover o ponteiro de versão atual, sem pacote pronto) e na imutabilidade por disciplina sobre uma tabela que o painel edita.
  • Shopify, WooCommerce, Magento, Saleor, Sylius e Odoo gravam nome, SKU e preço na linha. Nenhum aponta para versão de produto. Versionamento aparece como auditoria, que é outra pergunta: quem mudou o quê e quando.

Decisão

  • Colunas tipadas em order_items: sku, name, unit_price_cents, discount_cents, total_cents, mais product_id como referência navegável, nunca como fonte da venda.
  • Se for preciso guardar descrição e imagem como o cliente viu, coluna product_snapshot jsonb na mesma linha. Sem tabela nova, sem join.
  • Auditoria de produto via spatie/laravel-activitylog, que guarda o diff de cada edição sem tocar no modelo de vendas.
  • Nenhuma tabela de versões de produto.

Consequências

  • Renderizar um pedido não depende da tabela de produtos. Relatório por SKU é um GROUP BY em order_items.
  • order_items é append-only por natureza; a imutabilidade do histórico vem de não editar linhas de pedido, regra que já existe.
  • Soft delete em produtos garante que product_id nunca quebra; snapshot garante que o histórico nunca muda. Os dois mecanismos são complementares.
  • Reconstruir o catálogo inteiro numa data passada não é possível com este modelo. Se essa necessidade aparecer, versionamento volta à pauta como decisão separada.

9.6 Venda física é um pedido, não um ajuste de estoque

decidido em 03/11/2026

Contexto

O documento de requisitos original (UC04 e Cenário 3) trata a venda presencial como o administrador abrindo o produto e digitando o estoque novo, "de 20 para 15". Isso apaga o motivo da saída e é a maior fonte de divergência entre estoque físico e online, risco que o próprio documento classificou como probabilidade alta e impacto alto. O repositório atual faz o mesmo pelo PATCH /produtos/{id}/estoque.

Opções consideradas

  • A. Ajuste manual, como no documento. Simples na tela, cego no dado: a venda some do relatório e o estoque sai sem explicação.
  • B. Venda de balcão como pedido com channel = pos, itens, totais e pagamento. O ledger recebe sale apontando para o pedido.

Decisão

Opção B, nas palavras de Richard: "é registrar uma venda mesmo, não faz sentido baixa de estoque na mão". adjustment fica só para contagem, quebra e erro. O saldo nunca é editável no Filament; existem duas ações: registrar venda, que cria o pedido, e contagem / ajuste, em que o usuário informa o contado e o sistema grava a diferença com motivo.

Saldo negativo no balcão: permitido

O cenário não é vender o que não existe, é vender o que está na prateleira mas o sistema acha que não existe: entrada do fornecedor ainda não lançada, erro de contagem do mês passado. Bloquear faz a vendedora vender por fora e lançar depois, ou não lançar, e o ledger passa a mentir pior. Decisão de Richard: permitir, "se não vamos atrapalhar as vendas". O pedido pos passa, on_hand fica negativo e o painel mostra alerta "estoque negativo, lance a entrada ou faça contagem". Site e WhatsApp continuam bloqueando, porque o cliente remoto não vê a prateleira.

Consequências

  • Sem CHECK on_hand >= 0 em stock_levels. A regra "site não vende sem saldo" vive no serviço de reserva (available > 0), não no banco.
  • on_hand < 0 é sinal de divergência a tratar, não bug. Lista própria no painel.
  • Pedido pos nasce paid e delivered, sem endereço, sem frete, sem reserva. Movimento direto no ledger.
  • Relatórios de venda por canal saem de orders, sem somar ajustes.
  • O balcão precisa de uma tela de pedido rápida no painel: busca por SKU ou nome, quantidade, forma de pagamento, concluir.
  • Ainda aberto: seller_id, que depende do stakeholder.

9.7 Filtro por atributos e busca por texto

decidido em 03/11/2026: atributos genéricos, opção completa

Contexto

Os protótipos filtram a listagem por "Paleta de Cores" e "Tipo de produto", e a página do produto tem um "seletor de variações". Com catálogo plano (cada cor é um produto), falta um jeito de filtrar. Uma coluna color em products foi descartada como gambiarra: amanhã aparece tamanho, depois material, e cada um vira outra coluna, nula para metade do catálogo. Tags tipadas (spatie/laravel-tags) resolvem o filtro mas são texto livre. ILIKE é busca, não filtro, e não usa índice.

select p.*
from products p
where exists (select 1 from attribute_value_product avp
              where avp.product_id = p.id and avp.attribute_value_id in (1))
  and exists (select 1 from attribute_value_product avp
              where avp.product_id = p.id and avp.attribute_value_id in (4));

Lateral de filtros com contagem ("Azul (3)", "Rosa (1)"):

select a.name, av.value, count(*)
from attribute_value_product avp
join attribute_values av on av.id = avp.attribute_value_id
join attributes a on a.id = av.attribute_id
join products p on p.id = avp.product_id and p.is_active
group by a.name, av.value order by 1, 2;

Busca por texto é outra ferramenta

Na migration, $table->fullText(['name','description'])->language('portuguese') cria um índice GIN sobre to_tsvector. No Eloquent, Product::whereFullText(['name','description'], $termo). Não é over: uma linha de migration, e para algumas centenas de produtos custa nada. Nunca ILIKE para busca.

Consequências

  • Novo atributo é uma linha no painel, sem migration. Filtro de tamanho ou material entra de graça.
  • Eloquent: Product belongsToMany AttributeValue, AttributeValue belongsTo Attribute. Filtro vira um whereHas por atributo marcado.
  • Filament: um Select múltiplo por atributo no formulário de produto; resource simples para atributos e valores, que a dona gerencia sozinha.
  • O "seletor de variações" da página do produto vira só navegação entre produtos irmãos, se um dia for pedido.

9.9 Identidades do cliente em modelo próprio

decidido em 04/11/2026

Contexto

A atendente precisa achar o cliente pelo telefone (RF013). Um cliente pode ter mais de um número, pode trocar de número, e no futuro pode chegar por outras plataformas. Com phone e email como colunas únicas em customers, trocar de número apaga o histórico de busca e um segundo número não cabe. O erro do repo atual era criar conta com senha fake, não ter o registro do cliente.

customer_identities uma linha por contato do cliente, nunca apagada

  • Troca de número: aposenta a identidade antiga e insere a nova. Pedidos apontam para customer_id, então o histórico não se perde; o snapshot do pedido guarda o telefone usado na época.
  • Busca por telefone vai de identidade para cliente, incluindo aposentadas com indicação, para a atendente reconhecer "esse era o número antigo".
  • Um número ativo pertence a um cliente só; um número aposentado pode ser reatribuído a outra pessoa sem conflito.
  • customers fica com dados da pessoa: nome, CPF nullable com unique parcial, password nullable. Cliente de WhatsApp existe sem senha e ativa a conta depois por um contato já cadastrado.
  • Escopo esclarecido em 08/11/2026: esta tabela é sobre contatos e canais (mais de um número de WhatsApp, troca de número, outra plataforma no futuro), não sobre credencial. Login da loja continua padrão Laravel em customers.email e customers.password, ambos nullable. Sem UserProvider custom. Se um dia houver "login por WhatsApp", a identidade vira credencial como decisão separada.
